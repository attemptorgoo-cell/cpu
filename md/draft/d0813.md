这句话的核心是：让流水线区分“指令编码中某几位碰巧等于某个寄存器号”和“这条指令真的需要读取这个寄存器”。
1. decoder 在做什么
一条 32 位 RISC‑V 指令中，不同格式会复用相同的位段。例如：
instr[19:15] 在部分指令中是 rs1
instr[24:20] 在部分指令中是 rs2
但在其他格式中，这些位可能属于立即数，而不是寄存器编号
当前 decoder 在 [decoder.sv (line 30)](D:/03_uncompleted/cpu/vFile/verilog/verilog/decoder.sv:30) 中先执行：
decode_out = '0;
然后根据 opcode，只给该指令实际需要的字段赋值。例如：
R 型指令填写 rs1 和 rs2
ADDI 只填写 rs1
Load 只填写地址基址 rs1
Store 填写地址基址 rs1 和写入数据 rs2
LUI、AUIPC、JAL 不填写任何源寄存器
所以现在的 decoder 已经把 rs1/rs2 当成“语义化后的源寄存器”，而不是无条件复制原始指令位段。
2. 什么是 Load-use hazard
考虑：
lw   x5, 0(x1)
add  x6, x5, x2
第二条指令马上使用第一条 Load 要写回的 x5。
当前 RAM 是同步读。Load 处于 EX 阶段时，数据还不能及时提供给下一条指令的 EX 阶段，因此必须停一拍。
当前检测逻辑位于 [cpu.sv (line 102)](D:/03_uncompleted/cpu/vFile/verilog/verilog/cpu.sv:102)：
if (
    id_ex_bus.valid &&
    id_ex_bus_reg.valid &&
    id_ex_bus_reg.memory_re &&
    (id_ex_bus_reg.rd != 5'd0) &&
    (
        (id_ex_bus.rs1 == id_ex_bus_reg.rd) ||
        (id_ex_bus.rs2 == id_ex_bus_reg.rd)
    )
)
    stall = 1'b1;
这里：
id_ex_bus_reg：当前在 EX 阶段的旧指令，也就是可能产生结果的 Load
id_ex_bus：当前正在 ID 阶段译码的新指令，也就是可能消费结果的指令
id_ex_bus_reg.rd：Load 的目标寄存器
id_ex_bus.rs1/rs2：下一条指令的两个源寄存器
如果 Load 的 rd 等于下一条指令的任意源寄存器，就产生 stall。
3. stall 的一拍是怎么工作的
检测出依赖后：
PC 保持不变
IF 输出保持不变
IF/ID 流水寄存器保持当前消费者
ID/EX 流水寄存器写入全零 bubble
Load 自己继续向 MEM、WB 前进
相关逻辑在 [cpu.sv (line 72)](D:/03_uncompleted/cpu/vFile/verilog/verilog/cpu.sv:72) 和 [IF.sv (line 35)](D:/03_uncompleted/cpu/vFile/verilog/verilog/IF.sv:35)。
时序可以概括为：
时刻	EX	ID	动作
检测前	lw x5,...	使用 x5 的指令	stall=1
下一拍	bubble	消费者仍被保持	Load 进入 MEM
再下一拍	消费者	后续指令	Load 在 WB，数据通过 WB→EX 旁路送来


因此只需要停一拍。
4. 什么是假 stall
假 stall 是：两个数字看起来相等，但后面的指令其实根本不读取那个寄存器。
例如：
lw   x5, 0(x0)
addi x6, x0, 5
ADDI 的机器码为：
00500313
在 I 型指令中，instr[31:20] 是立即数。这里立即数是 5，所以 instr[24:20] 也恰好是二进制 00101，数值上等于寄存器号 x5。
但这并不意味着：
addi x6, x0, 5
会读取 x5。它只读取 rs1=x0，第二个操作数来自立即数。
如果设计无条件把：
rs2 = instr[24:20];
再进行：
rs2 == load_rd
那么它会错误地认为 ADDI 依赖 x5，从而多停一拍。这就是“字段相等但不是真实依赖”。
5. uses_rs1、uses_rs2 表示什么
这两个信号是 decoder 对指令语义的明确说明：
uses_rs1 = 1;
表示这条指令真的会读取 rs1。
uses_rs2 = 1;
表示这条指令真的会读取 rs2。
各类指令应当如下：
指令类型	uses_rs1	uses_rs2	原因
JAL	0	0	使用 PC 和立即数
JALR	1	0	跳转目标使用 rs1 + imm
Branch	1	1	比较两个寄存器
LUI	0	0	只使用立即数
AUIPC	0	0	使用 PC 和立即数
Load	1	0	rs1 是地址基址
Store	1	1	rs1 是地址，rs2 是写入数据
OP-IMM	1	0	使用 rs1 和立即数
R 型 OP	1	1	使用两个寄存器
未知指令	0	0	默认不声明依赖


尤其要注意 Store：
sw x5, 0(x1)
它既使用 x1 计算地址，也使用 x5 作为待写数据，因此必须是 (1,1)。
不能简单根据 imm_we 推导 uses_rs2，因为 Store 虽然使用立即数计算地址，同时仍然读取 rs2。
6. 修改后 hazard 应怎样判断
改造后的核心条件应是：
(
    id_ex_bus.uses_rs1 &&
    (id_ex_bus.rs1 == id_ex_bus_reg.rd)
) ||
(
    id_ex_bus.uses_rs2 &&
    (id_ex_bus.rs2 == id_ex_bus_reg.rd)
)
完整逻辑仍然必须保留：
id_ex_bus.valid
id_ex_bus_reg.valid
id_ex_bus_reg.memory_re
id_ex_bus_reg.rd != 0
也就是说，只有同时满足以下条件才能 stall：
消费者是一条有效指令。
生产者是一条有效指令。
生产者确实是 Load。
Load 的目标不是 x0。
消费者真的使用相应源寄存器。
该源寄存器等于 Load 的目标寄存器。
rd != 0 很重要，因为写入 x0 的结果会被丢弃，后面的指令不可能依赖这个结果。
7. 这两个信号要经过哪些模块
需要经过的路径是：
decoder
   ↓
decode_out_t
   ↓
ID
   ↓
id_ex_bus_t
   ↓
CPU 的 stall 检测
具体位置：
在 [package.sv (line 3)](D:/03_uncompleted/cpu/vFile/verilog/verilog/package.sv:3) 的 decode_out_t 中增加：

logic uses_rs2;
在 [package.sv (line 39)](D:/03_uncompleted/cpu/vFile/verilog/verilog/package.sv:39) 的 id_ex_bus_t 中增加同样两个字段。

在 [decoder.sv (line 33)](D:/03_uncompleted/cpu/vFile/verilog/verilog/decoder.sv:33) 的各个 opcode 分支中设置它们。

在 [ID.sv (line 56)](D:/03_uncompleted/cpu/vFile/verilog/verilog/ID.sv:56) 中传递：

id_ex_bus.uses_rs1 = decode_out.uses_rs1;
id_ex_bus.uses_rs2 = decode_out.uses_rs2;
在 [cpu.sv (line 102)](D:/03_uncompleted/cpu/vFile/verilog/verilog/cpu.sv:102) 中用它们门控比较。
这两个信号只服务于“ID 指令是否依赖 EX 中的 Load”，因此暂时不需要继续传到 EX/MEM 或 MEM/WB。
8. 当前代码需要特别澄清的地方
检查 RTL 后发现：当前版本并没有一个能够用合法已支持指令稳定复现的假 stall。
原因是 decoder 已经通过：
decode_out = '0;
加上“只给实际使用的 rs1/rs2 赋值”，隐式屏蔽了未使用字段。例如 ADDI 的 rs2 会保持为零，而不是复制 instr[24:20]。
所以这里更准确的描述不是“当前已经确认存在假 stall bug”，而是：
当前正确性依赖一项隐式约定：所有未使用的 rs1/rs2 必须保持为零。uses_rs1/uses_rs2 会把这项约定改成明确、可验证的接口语义。

这样做的价值包括：
将“寄存器编号”和“寄存器是否被使用”分离。
将来统一提取原始指令字段时不会引入假 stall。
扩展新指令时不容易漏掉依赖语义。
测试可以直接检查 decoder 是否正确声明源操作数。
hazard 逻辑不再依赖“未使用字段碰巧为零”。
因此，这项改动更像是消除设计中的隐式耦合，并预防未来回归，而不是修复当前已经能够观察到的执行错误。


先说明口径：当前路线图里的 Tcl 自动回归、绝对路径清理仍应在大改前完成，但它们不是你路上要推演的微架构 SV，所以不占这三个名额。

排除 `uses_rs1/uses_rs2` 后，我建议按以下顺序迭代：

```text
源寄存器是否使用
→ 源数据在哪一级使用
→ 内存延迟不固定时如何保持流水线
→ 指令出错时如何精确地 kill/redirect
```

## 一、Load→Store-data 的晚旁路

### 内容

优化这种序列：

```assembly
lw x5, 0(x0)
sw x5, 4(x0)
```

当前 Load-use 检测会认为 Store 使用了 `x5`，于是停一拍。相关判断本身没有错，但它忽略了一个更细的问题：

> Store 的 `rs2` 数据不是在 EX 使用，而是在 MEM 真正写 RAM 时才使用。

时间上，Store 到达 MEM 时，前面的 Load 已经到 WB，Load 数据可以直接从 WB 旁路到 MEM。因此这种“只依赖 Store 写数据”的情况不必停顿。

这一步是 `uses_rs1/uses_rs2` 的自然延伸：

- `uses_rs*` 回答“是否使用”
- 晚旁路回答“在哪一级使用”

### 必须满足的行为

对于 Store：

- `rs1` 是地址基址，在 EX 计算地址，必须及时得到。
- `rs2` 是写入数据，可以推迟到 MEM 获得。

所以三种情况应明确区分：

| 序列 | 依赖类型 | 预期 |
|---|---|---|
| `lw x5,...; sw x5,4(x0)` | 仅 Store 数据依赖 | 0 次 stall |
| `lw x5,...; sw x1,0(x5)` | Store 地址依赖 | 1 次 stall |
| `lw x5,...; sw x5,0(x5)` | 地址和数据同时依赖 | 1 次 stall |

具体设计要求：

- Store 的 `rs2` 编号必须保留到 EX/MEM。
- MEM 的 Store 写数据前增加最终选择：
  - 如果 WB 是有效写回；
  - WB 的 `rd != x0`；
  - WB 的 `rd == MEM Store.rs2`；
  - 那么使用 WB 数据，否则使用原 Store 数据。
- Store 地址绝不能使用这条晚旁路；地址仍在 EX 解决。
- 旁路只改变数据来源，不能让 Store 写两次。
- Store 无效或被 flush 时不能写 RAM。
- 不要简单写成“Store 永远不检查 rs2 依赖”；只有具备 WB→MEM 晚旁路后才能取消这类 stall。

### 验收重点

专项测试应同时包含纯数据依赖、纯地址依赖和双依赖，检查：

- RAM 最终内容；
- stall 总数；
- 每条 Store 只提交一次。

按现有测试内容推算，完成优化后：

- Test 11 的 stall 数应由 4 降到 3；
- Test 12 的 stall 数应由 10 降到 9；
- 所有寄存器和 RAM 结果保持不变。

已经归档的 Test 11/12 不应修改；新基线应建立新的测试编号和期望结果。

## 二、单 outstanding 的请求/响应式数据内存与流水线背压

### 内容

当前同步 RAM 的延迟固定。Load 发出后，设计知道数据将在指定周期出现，因此“一拍 Load-use stall”足够。

但是 Cache、外部总线和慢速内存都可能出现：

- 当前周期不接受请求；
- 接受请求后过若干周期才返回结果；
- 不同请求的等待时间不同。

因此下一次真正重要的流水线升级，是把数据 RAM 边界改成请求/响应形式。

第一版只做：

- 数据侧；
- 最多一个未完成请求；
- 不做 Cache；
- 不做多个 outstanding；
- 不做乱序响应。

### 接口契约

请求侧至少应表达：

```text
req_valid
req_ready
地址
读/写类型
写数据
字节写掩码
```

响应侧至少应表达：

```text
resp_valid
resp_ready
读数据
```

建议第一版让 Load 和 Store 都有完成响应；Store 的响应数据可以忽略。这样两类访存的“何时完成”规则一致。

核心握手规则是：

```text
request_fire  = req_valid  && req_ready
response_fire = resp_valid && resp_ready
```

只有 `fire` 才表示事件真的发生。

### 必须满足的行为

1. 请求等待时内容稳定

当：

```text
req_valid=1，req_ready=0
```

地址、操作类型、写数据和字节掩码都必须保持不变。

2. 请求只能发送一次

EX/MEM 中的访存指令可能停留很多周期，但不能每周期都重新发请求。需要区分：

- 请求尚未接受；
- 请求已经接受，正在等待响应；
- 响应已经完成。

3. Store 只能写一次

不能因为流水寄存器保持而重复写 RAM。Store 的副作用必须绑定到一次明确握手或一次明确提交事件。

4. 保存 Load 上下文

等待响应期间必须保存：

- `rd`
- 地址低位
- Load 类型 `func3`
- 是否写回
- 其他完成 Load 格式化所需的信息

响应回来时，必须仍然知道数据属于哪条 Load。

5. 正确冻结流水线

当 MEM 中有未完成请求时：

- EX/MEM 不能被年轻指令覆盖；
- EX、ID、IF 中的年轻指令必须保持；
- 更老的 WB 指令应允许完成一次；
- 已经完成的 WB 不能因为保持而连续写回多次。

这不是简单的“所有寄存器一起 freeze”，而是按照指令年龄决定谁能继续、谁必须保持。

6. 统一控制决策

当前 [cpu.sv](D:/03_uncompleted/cpu/vFile/verilog/verilog/cpu.sv:84) 的 redirect 和 [stall](D:/03_uncompleted/cpu/vFile/verilog/verilog/cpu.sv:94) 是两个独立的 `if`，后面的赋值可能覆盖前面的赋值。固定一拍 stall 时通常碰不到冲突，但引入内存等待后会变成真实问题。

需要统一定义每一级的：

```text
advance / hold / kill
```

并形成唯一、互斥的控制决策。

一个重要原则是：

> 更老的 MEM 指令正在等待时，年轻 EX 指令即使已经算出 branch redirect，也应先保持；等老指令完成后，再让 branch 产生一次 redirect。

否则会出现重复 redirect、丢失 JAL link 或年龄顺序混乱。

7. 晚旁路数据需要锁存

第一项中的 WB→MEM Store-data 旁路，在可变延迟下不能一直依赖瞬时 WB 信号。Store 请求形成时就应选出最终写数据，并将它锁存到请求上下文中；随后等待 `req_ready` 时保持稳定。

### 验收重点

测试内存应能注入：

- 0 拍等待；
- 1 拍等待；
- 固定 N 拍等待；
- 最好再加入伪随机等待。

检查：

- 请求没有丢失；
- 请求没有重复；
- Store 没有重复提交；
- outstanding 数始终不超过 1；
- `valid && !ready` 时请求内容稳定；
- 被保持的 branch/JAL 不会重复 redirect；
- Load 返回后消费者得到正确数据；
- 错误路径 Store 的请求次数为零。

零等待配置下，现有全部架构结果必须保持。

建议将 `load_use_stall_count` 和 `memory_wait_count` 分开统计，不要把两种等待混成一个数字。

## 三、严格非法指令译码与最小精确 trap

### 内容

当前 decoder 的默认清零可以挡住未知 opcode，却不一定能挡住：

> opcode 合法，但 `funct3/funct7` 不属于已实现指令的编码。

例如不支持的 M 扩展 `MUL` 仍使用 R 型 opcode。当前 R 型分支会提前拉高寄存器写使能，而 ALU 操作默认可能落到 ADD，于是非法指令可能错误地变成一条 ADD。

类似风险还包括：

- 非法 Load `funct3` 仍拉高 `memory_re`；
- 非法 Store `funct3` 仍进入 Store 路径；
- JALR 没有严格要求 `funct3=000`；
- 非法移位指令的 `funct7` 未被完整拒绝。

所以这一步不是添加大量 CSR，而是先建立一个最小、精确的错误处理骨架。

### 严格译码要求

decoder 必须按完整编码判断是否合法，例如：

- JALR 只接受 `funct3=000`；
- Branch 只接受六个规定的 `funct3`；
- Load 只接受 LB/LH/LW/LBU/LHU；
- Store 只接受 SB/SH/SW；
- 移位立即数必须检查合法 `funct7`；
- R 型只接受当前实现的组合；
- SYSTEM、FENCE、M 扩展在尚未实现时都应标记非法。

需要注意：

- `valid` 表示流水槽里有一条指令；
- `illegal` 表示这条有效指令发生异常。

不能把非法指令直接当 bubble，否则以后无法知道其 PC 和机器码，也就无法产生精确 trap。

非法指令还必须立即隔离普通副作用：

```text
reg_we     = 0
memory_re  = 0
memory_we  = 0
普通 redirect = 0
```

但仍要保留：

- `illegal`
- 指令 PC
- 原始 32 位指令

### 最小 trap 要求

第一版只需要：

- 一个固定、位于指令 ROM 范围内的 trap vector，例如 `0x80`；
- `mepc`：故障指令 PC；
- `mcause`：非法指令为 2；
- `mtval`：原始机器码；
- trap redirect；
- 暂时不实现 CSR 指令、中断、特权级和 `mret`。

精确性的定义是：

- 比故障指令更老的指令可以完成；
- 故障指令自身不得写寄存器或内存；
- 比故障指令年轻的指令全部清除；
- PC 跳到 trap vector；
- handler 只执行一次。

如果更老的 MEM 指令还在等待，年轻的非法指令必须先保持，不能抢在老指令前触发 trap。这正是把本项放在可变延迟内存之后的原因。

### 验收重点

可以用未实现的 MUL 编码作为第一条非法指令：

```assembly
.word 0x020000b3
```

测试布局应是：

```text
建立寄存器和 RAM sentinel
→ 放置一条应正常提交的老指令
→ 非法指令
→ 放置年轻的 ADDI 和 Store
→ trap handler 写入 marker
→ 稳定自环
```

期望检查：

- 老指令结果保留；
- 非法指令目标寄存器不变；
- 年轻 ADDI 不执行；
- 年轻 Store 不改变 sentinel；
- handler marker 正确；
- `trap_count=1`；
- `mepc` 等于非法指令 PC；
- `mcause=2`；
- `mtval=0x020000b3`。

还应分别用非法 Load `funct3`、非法 JALR `funct3` 做抽查，证明它们不会产生内存请求或普通跳转。

你路上可以一直抓住这三个问题思考：

1. 同样是寄存器依赖，这个值究竟在哪一级才必须出现？
2. 一个事件等待很多周期时，哪些级保持、哪些老指令还能完成，以及如何保证事件只发生一次？
3. 一条指令出错时，哪些更老指令应该保留，故障指令和哪些年轻指令必须被杀死？

这三个问题分别对应晚旁路、背压和精确异常，也是从当前固定五级流水线继续向真实处理器控制模型迈进的最自然路径。
