# 从自研五级流水线到香山：项目总览与智能体交接

Updated: 2026-08-12

## 0. 先理解这个项目到底要做什么

这个仓库当前虽然只有一个小型 RV32I 五级流水线核，但最终目标不是停留在“补完一个课程 CPU”。用户希望以自己写出的 SystemVerilog 五级核为实验基线，逐步学习、实现和验证现代高性能处理器机制，最终能够读懂、运行、追踪并低风险修改香山处理器源码。

项目的长期目标包括三个相互联系、但不能混为一谈的方向：

1. **保留并完善自研 CPU**：它承担最小实验平台和认知参照物的角色。新的控制、缓存、异常或乱序概念，优先在这个可观察的小核中建立最小模型。
2. **学习香山的微体系结构**：理解 Frontend、Backend、MemBlock、ROB/Commit、LSU、Cache、TLB、分支预测、重命名、调度、重放和恢复机制为何存在以及如何协作。
3. **进入真实香山工程**：学习 Scala/Chisel、参数化配置、Diplomacy、TileLink、Difftest 和官方构建流程，固定分支与 commit 后沿事件路径阅读和验证源码。

不要把“实现香山 CPU”理解成在当前 `IF/ID/EX/MEM/WB` 文件中不断加入功能，直到它自然变成香山。二者规模和组织方式不同：

```text
当前工程
  = 单发射 + 顺序执行 + 架构寄存器直接读写 + 固定五级 + 简单组合 RAM

香山
  = 宽取指/多发射 + 推测前端 + 寄存器重命名 + 乱序调度/执行
    + ROB 顺序提交 + 复杂 LSU + Cache/TLB + 精确异常 + 参数化 Chisel 工程
```

当前小核应该被视为“机制实验室”和“对照组”，而不是未来香山源码的结构模板。

## 1. 最终验收目标

项目完成时，用户应能做到：

1. 从空白纸画出香山单核的 Frontend、Backend、MemBlock、ROB/Commit、缓存和互连边界。
2. 把一条标量 ALU 指令从 PC 生成一路追踪到 Commit，并说明每阶段的 valid、ready、阻塞和恢复条件。
3. 完整解释一次分支误预测：预测、FTQ 上下文、执行发现错误、redirect 仲裁、年轻指令冲刷、Rename/ROB 恢复和预测器更新。
4. 完整解释一次 Load hit、Load replay、DCache miss 和 Store commit。
5. 区分架构状态、推测状态和普通微体系结构状态，并解释乱序核如何提供精确异常。
6. 从配置参数找到真实实例，从顶层接口找到具体模块，再从静态源码回到波形或日志验证结论。
7. 在香山中完成一次低风险修改，例如断言、日志、性能计数器或局部策略，并通过官方测试/Difftest 回归。
8. 将香山的每个关键机制映射回当前五级核，回答“如果仍用这个小核，为什么会停顿或做不到”。

## 2. 当前五级核与香山的结构映射

下面的映射是整个项目的大局观。每实现或学习一个机制，都应更新这张表，而不是只记住新文件名。

| 当前五级核 | 当前行为 | 香山中对应或扩展的结构 | 香山解决的新问题 |
|---|---|---|---|
| `IF.sv` | PC 每拍 `+4`，EX redirect 后改 PC，ROM 直接出指令 | Frontend、BPU、FTQ、ICache、ITLB、预解码、IBuffer | 宽取指、提前预测、可变延迟取指、保存预测上下文与恢复 |
| `IF/ID` 总线 | 单条指令和 PC，加一个 valid | 取指块/指令队列的多路 Decoupled 接口 | 多条指令并行流动、局部回压、队列解耦 |
| `decoder.sv` / `ID.sv` | 译码后直接读取架构寄存器 | Decode、微操作生成、Rename、RAT、Free List、物理寄存器堆 | 消除 WAR/WAW，保存多个寄存器版本，支持推测恢复 |
| 当前 stall/旁路 | 固定优先级旁路或全局保持 | Dispatch、Issue Queue、busy table、wakeup/select、ready/valid | 不让一个未就绪操作数阻塞所有无关指令 |
| `EX.sv` | 单个 ALU、分支比较、固定组合旁路 | 多执行块、多端口、多周期单元、旁路/写回网络、仲裁 | 多条不同延迟指令并行执行并正确广播结果 |
| `branch_sign` + 清零两级 | EX 发现跳转后清 IF/ID、ID/EX | redirect 网络、FTQ、checkpoint、Rename/ROB 恢复、各队列 flush | 恢复深而宽的推测流水线和多种状态 |
| `MEM.sv` + `ram.sv` | 组合读 RAM、同步写、简单字节选择 | LSU、AGU、LQ/SQ、DTLB、PTW、DCache、MSHR、replay | 地址翻译、内存依赖预测、Store 转发、miss 和违例重放 |
| `WB.sv` | 结果直接写架构寄存器 | 写回仲裁、物理寄存器写回、ROB 完成状态 | 执行完成不等于软件可见，多个结果争用写回端口 |
| WB 即“完成” | 写回后自然结束 | ROB、Commit、精确异常、CSR | 内部乱序完成，但架构状态必须按程序顺序生效 |
| `package.sv` 固定 Bundle | 固定位宽、固定单发射结构 | 参数化 Bundle、配置系统、Chisel 生成式硬件 | 用同一源码生成不同宽度、队列深度和特性组合 |
| 简单 RAM 接口 | 无总线协议、无缓存一致性 | TileLink、L1/L2、inclusive cache、系统互连 | 可缓存事务、多主设备、一致性与可变延迟响应 |

这张表不是说当前文件要一对一重写成香山模块。它的用途是帮助用户从已经真正理解和仿真过的机制出发，推导大型乱序核为什么需要额外状态。

## 3. 香山整体视角

从学习角度，可以先把香山单核压缩为下图：

```text
                         redirect / recovery
                    +-----------------------------+
                    |                             |
                    v                             |
+---------------- Frontend ----------------+      |
| PC/BPU -> FTQ -> ICache/ITLB -> IBuffer   |      |
+--------------------+----------------------+      |
                     | decoded instruction stream  |
                     v                              |
+---------------- Backend -----------------------+ |
| Decode -> Rename -> Dispatch -> Issue Queues   | |
|                    |              |             | |
|                    |              v             | |
|                    |      Execution Units ------+-+
|                    |              | writeback   |
|                    v              v             |
|                  ROB ----------> Commit         |
+--------------------+----------------------------+
                     |
                     | load/store uops
                     v
+---------------- MemBlock / LSU -----------------+
| AGU -> LQ/SQ -> DTLB/PTW -> DCache -> replay    |
|                  |                     |         |
|                  +---- exceptions -----+         |
+--------------------+----------------------------+
                     |
                     v
             L2 / TileLink / memory system
```

### 3.1 Frontend 不只是 IF

当前 `IF.sv` 等到 EX 给出实际分支结果才改变 PC。高性能前端不能这样等待，因为分支解析前可能需要取出许多后续指令。

香山前端的核心循环应理解为：

```text
猜测下一段 PC
-> 保存预测上下文
-> 取出指令字节
-> 形成可供后端消费的指令流
-> 后端发现真实结果
-> redirect、flush、预测器更新
-> 从恢复 PC 再次预测
```

需要重点追踪的状态包括预测历史、FTQ 项、取指请求、ICache/ITLB 状态和后端 redirect。当前 `branch_sign` 是理解这整条恢复链的最小原型。

### 3.2 Backend 的关键不是“级数更多”，而是拆开顺序再合上

顺序核中，一条旧指令停住时，年轻指令通常整体跟着停。乱序后端通过以下机制寻找并行：

```text
Decode
-> Rename 消除 WAR/WAW
-> Dispatch 分配队列和 ROB 项
-> Issue Queue 等待操作数和执行端口
-> 就绪指令可以越过未就绪旧指令执行
-> Writeback 标记完成并唤醒消费者
-> ROB 仍按程序顺序 Commit
```

因此 Rename/Issue/ROB 是一条连续因果链，不能作为三个无关模块分别背诵：

- Rename 让多个寄存器版本同时存在；
- Issue 利用这些版本的 ready 状态进行乱序选择；
- ROB 保存原始程序顺序并提供恢复与精确异常边界。

### 3.3 MemBlock 是前面所有机制的交汇点

当前 MEM 只根据地址读写一个数组。真实 Load/Store 需要同时处理：

- 地址计算；
- 虚拟到物理地址翻译；
- 权限与异常；
- 与更老 Store 的地址/数据依赖；
- Store-to-Load forwarding；
- DCache hit/miss；
- miss 请求和 refill；
- 推测执行后发现违例时 replay；
- Store 只有在正确提交后才能安全成为架构可见状态；
- Fence、AMO、MMIO 和内存模型约束。

这就是当前 load-use stall 讨论不能只理解为“一根 stall 线”的原因。它是未来从固定延迟内存走向请求/响应、队列和 replay 的入口。

### 3.4 ROB/Commit 是当前小核最缺失的语义边界

当前核的结果到 WB 就直接修改架构寄存器。香山内部允许指令乱序执行和完成，因此必须区分：

```text
执行完成：结果已经算出
写回完成：结果进入物理寄存器或完成网络
提交/退休：结果按程序顺序正式成为软件可见状态
```

分支误预测、异常、中断和访存重放都依赖这个区分。未来在自研核中加入一个最小 ROB，比单纯增加更多 ALU 更能帮助理解香山。

## 5. 从当前工程走向香山的阶段路线

### 阶段 A：封存可信的顺序核基线（当前阶段）

目标不是无限补测试，而是让这个小核成为后续实验的可信参照。

已完成：

- valid 贯穿主要流水总线；
- 分支/JAL/JALR redirect 与年轻指令 flush；
- ALU/MEM/WB 旁路；
- RV32I 主要整数、分支、跳转和访存功能；
- 自检 testbench；
- 10 组已确认通过并归档的定向回归。

尚未完成：

- 正确、可验证的 stall/hold/bubble 控制；
- 同步 RAM 或请求/响应式内存接口；
- 非法指令、异常、CSR、中断；
- RV32I 完整规范审计和对齐异常；
- 自动执行全部归档测试的回归脚本。

阶段 A 的结束条件：能够闭卷解释 valid、forward、flush、stall 的差异，并用波形指出每种控制发生时各级保存或清除什么。

### 阶段 B：补齐软件可见的 RISC-V 模型

重点不是立即做乱序，而是理解处理器对软件的承诺：

1. 从 C、ELF、链接和 ABI 追到机器码；
2. 从当前 RV32I 过渡到 RV64I；
3. 学习 M/A/C 扩展和浮点/向量基本语义；
4. 加入 CSR、异常、中断和最小 trap 流程；
5. 学习 M/S/U 特权级、Sv39、TLB/PTW/PMP；
6. 理解 RVWMO、Fence、AMO 以及 RVV 的基本状态。

如果没有这一阶段，后面看到香山 CSR、TLB、LSU 或向量源码时，只会知道信号在流动，却不知道它们正在兑现哪条 ISA 承诺。

### 阶段 C：从顺序流水推导乱序机制

推荐以小型模型或模拟器逐项加入：

```text
性能指标/CPI
-> Cache 与可变延迟
-> 分支预测
-> 物理寄存器和 Rename
-> Dispatch/Issue/wakeup-select
-> ROB/Commit/精确异常
-> LQ/SQ/内存依赖/replay
```

每一项都必须回答：

1. 当前五级核为什么会整体停住或无法正确执行？
2. 新结构保存了什么额外状态？
3. 发生分支失败、异常或 replay 时，这些状态怎样清除或恢复？

### 阶段 D：学习香山的表达语言与互连

顺序建议：Scala 阅读基础 -> Chisel 硬件语义 -> Decoupled/Queue -> FIRRTL/生成 RTL -> LazyModule/Diplomacy -> TileLink。

这一阶段最重要的视角转换是：

```text
Scala 在 elaboration 时构造硬件
!=
生成后的寄存器和组合逻辑在每拍运行
```

用户当前在 SystemVerilog 中学习的 valid/stall/flush，未来要提升为模块局部的 ready/valid 和 backpressure；香山并不是由一根全局 stall 控制所有模块。

### 阶段 E：运行香山并建立源码地图

在原生 Linux 或 WSL2 中：

1. 固定 kunminghu-v3 commit 和配置；
2. 初始化子模块并记录工具版本；
3. 构建官方仿真器；
4. 跑最小镜像和 Difftest；
5. 故意制造一次失败，理解错误报告；
6. 只读顶层、配置和接口，建立 System/Tile/Core -> Frontend/Backend/MemBlock 地图。

不要从 `src/main/scala` 第一行顺序阅读。源码入口应该是一个具体事件或一条具体指令。

### 阶段 F：沿事件路径读香山

至少保存以下动态追踪：

1. 普通标量 ALU 指令；
2. 分支预测命中；
3. 分支误预测和 redirect；
4. ICache miss；
5. Load hit；
6. Load replay；
7. DCache miss/refill；
8. Store commit；
9. 页故障或其他精确异常；
10. 向量算术与向量访存各一条。

每条追踪必须同时记录输入、关键周期、模块/信号、状态变化、结束条件、源码位置、波形或日志证据，以及和当前五级核的差异。

## 6. 四条贯穿整个项目的主线

为了避免知识碎片化，后续智能体必须尽量把工作挂到以下四条主线上。

### 6.1 普通整数指令

```text
C/ELF -> 机器码 -> 取指 -> 译码 -> Rename -> Dispatch
-> Issue -> Execute -> Bypass/Writeback -> ROB -> Commit
```

当前小核已经覆盖了机器码、取指、译码、执行、旁路和架构寄存器写回。缺失的是 Rename、Issue、ROB 和真正的 Commit 边界。

### 6.2 分支误预测

```text
BPU 预测 -> FTQ 保存上下文 -> 错误路径继续流动
-> 分支执行发现错误 -> redirect 仲裁
-> Frontend/Backend 队列 flush -> Rename/ROB 恢复
-> 从正确 PC 重新开始 -> 更新预测器
```

当前 `branch_sign`、`ex_if_bus.pc_branch` 和清空 IF/ID、ID/EX 是这条链最小、非推测版本的原型。

### 6.3 Load miss 或 replay

```text
AGU -> 地址翻译 -> LQ/SQ 依赖检查 -> DCache
-> hit / miss / forwarding / replay
-> 写回并唤醒消费者 -> ROB 完成 -> Commit
```

当前组合 RAM 的 load-use 旁路只是最简单的 hit 模型；同步 RAM 讨论是从固定延迟进入可变延迟的第一步。最终不能依靠固定一拍 stall 解释 Cache miss，而需要请求/响应、队列和 replay。

### 6.4 精确异常

```text
某阶段发现异常 -> 把异常记录到指令/ROB 项
-> 年轻指令可以被阻止提交
-> 异常指令到 ROB 头部
-> 更新 CSR、选择异常向量、redirect
-> 清除推测状态
```

当前核没有 CSR、ROB 或异常，因此这条主线尚未开始。它将是解释“内部乱序但软件观察仍然顺序”的关键。

## 8. 当前工程的架构与数据流

当前核是一个单发射、顺序执行的 RV32I 五级流水线：

```text
IF -> IF/ID -> ID -> ID/EX -> EX -> EX/MEM -> MEM -> MEM/WB -> WB
```

数据相关主要依靠：

```text
MEM -> EX forwarding
WB  -> EX forwarding
WB  -> ID register-file read-through
```

控制相关依靠 EX 阶段解析后 redirect，并清空两条年轻指令。RAM 当前是组合读、同步写，因此形成一条较长的组合 Load 路径。

## 11. 当前未提交的 RTL 草稿

`vFile/verilog/verilog/cpu.sv` contains an unfinished `stall` draft:

- `logic stall` is declared but is not driven.
- The final `if (stall)` is separate from the branch decision, so it can override branch flush assignments in the same `always_ff` block.
- It currently holds both `if_id_bus_reg` and `id_ex_bus_reg`. A one-cycle load-use stall must instead hold IF/ID and insert a bubble into ID/EX, while the older Load continues into EX/MEM.
- IF has no stall/hold input yet, so its PC and output continue advancing.
- The current draft has not been validated by the archived regression tests.

Do not describe the stall feature as complete and do not archive a stall test until the implementation passes Vivado.

The intended top-level priority is:

```text
reset > redirect/flush > stall > normal advance
```

For a load-use stall:

```text
PC and IF output: hold
IF/ID: hold the dependent instruction
ID/EX: insert valid=0 bubble
EX/MEM: advance the older Load
MEM/WB: advance normally
```

## 12. 当前最重要的设计分岔：内存时序

The current RAM is combinational-read:

```text
address -> RAM data -> MEM load formatting -> MEM-to-EX forwarding
```

That is why an immediately dependent instruction currently works without a stall.

Do not mechanically replace the RAM read with `always_ff` while retaining an additional MEM/WB register. That creates two registered boundaries:

```text
synchronous RAM output register -> MEM/WB pipeline register
```

In that form, Load data reaches WB later and requires a multi-cycle wait or a `data_valid/ready` protocol.

Recommended next design:

1. First finish a clean hold/bubble/flush controller while leaving RAM behavior unchanged.
2. Then redesign the synchronous RAM output as the MEM/WB data boundary, delaying `valid`, `rd`, `we`, `func3`, and address-low bits alongside the RAM data.
3. With that boundary, a one-cycle load-use stall can place the consumer in EX when the Load is in WB, using WB-to-EX forwarding.
4. Keep MEM-to-EX forwarding for ordinary ALU results.

Alternative design: keep both a registered RAM output and MEM/WB register, but then use a memory response-valid handshake instead of assuming a fixed one-cycle stall. This is closer to future Cache behavior but is a larger change.

## 17. 对接手智能体的工作原则

1. **让用户继续亲手写关键 RTL。** 用户正在通过设计、犯错、看波形形成硬件时序直觉。除非用户明确要求代写，不要把所有实现直接完成后交付；应优先检查、指出因果、给出最小修改方向，并由智能体承担重复性测试工作。
2. **自动承担验证劳动。** 机器码生成、`test.sv initial` 检查、通过后的 `.hex/.svh/README` 归档属于智能体职责，具体规则见 `AGENTS.md`。
3. **每次局部工作都挂回香山。** 例如学习 stall 时，需要说明它如何演进为 Decoupled backpressure；学习 branch flush 时，需要说明它如何演进为 FTQ/ROB/Rename 恢复；学习同步 RAM 时，需要说明它如何演进为 LSU/DCache 的响应与 replay。
4. **不提前堆砌香山名词。** 映射到香山的目的是建立因果关系，不是把当前模块改名为 FTQ、ROB 或 LSU。概念没有最小实验和动态证据时，不算掌握。
5. **区分事实、推导和未来设计。** 当前 RTL 行为、已通过测试属于事实；对同步 RAM 的方案属于设计选择；香山具体类名、宽度和队列深度必须在固定源码配置中验证。
6. **保留用户修改。** 工作区可能有未提交内容，绝不能用 reset/checkout 覆盖。先看 `git diff`，再围绕现状工作。
7. **不要让文档取代实验。** 每个阶段至少保留代码、测试、Vivado 波形或日志中的一种动态证据。

如果用户希望继续理解而非直接编码，应先用以下周期表讨论：

```text
周期 T:   Load 在 EX，消费者在 ID
周期 T+1: Load 在 MEM，EX 是 bubble，消费者仍在 ID
周期 T+2: Load 在 WB，消费者在 EX，通过 WB->EX 获取数据
```

然后明确：这张表只适用于“同步 RAM 输出作为 MEM/WB 边界”的方案；若同步 RAM 输出后还有一层 MEM/WB 寄存器，就需要额外等待或 response-valid 握手。
